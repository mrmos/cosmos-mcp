# Cosmos GraphQL — schema discovery

Endpoint: `POST https://api.cosmos.so/graphql?q=<OperationName>`

Required headers:

```
content-type: application/json
x-client-name: cosmos-web
origin: https://www.cosmos.so
referer: https://www.cosmos.so/
accept: application/graphql-response+json,application/json;q=0.9
```

Introspection is disabled (`INTROSPECTION_NOT_ALLOWED`). Everything below was
recovered **without authenticating**, by reading GraphQL *validation* errors,
which the server returns alongside the `AUTHENTICATION` error.

Reproduce with `bun run scripts/probe-schema.ts <round>`; the probe sets are
generated by `scripts/gen-round2.ts`, `gen-round3.ts`, `gen-round4.ts`,
`gen-round5.ts`. ~1640 probes were issued at 120 ms spacing; no rate limiting
was ever hit.

A second, independent source corroborates much of this: the cosmos-web Next.js
bundles (144 chunks, 12 MB) carry 261 GraphQL operation documents inline. Those
gave real operation text and real call-site input shapes; every name taken from
them was then re-probed against the live schema before being listed as
confirmed. Rows tagged `BUNDLE` were found in the client first.

**The two sources disagree in one direction only, and the probe wins.** The
client does not use `element.disconnectElementsFromCluster`,
`cluster.reorderElement`, or `EditClusterInput` — it uses
`editElementsConnectionsToClusters`, a client-side array reorder, and
`UpdateClusterInput`. But all three exist on the server; probes confirm them
directly. Absence from the web client is not absence from the schema.

## How each fact was confirmed

| Evidence code | Meaning |
| --- | --- |
| `TYPE` | Selected a nonsense sub-field `zzzProbe`. Error `Cannot query field 'zzzProbe' on type 'T'.` proves the parent field exists **and** names its return type `T`. |
| `ARG` | Omitted the argument. Error `Argument 'input' of type 'X!' is required for field 'f'` names the argument and its input type. |
| `REQ` | Sent `input: {}`. Error `Missing required field 'f' of type 'T'.` enumerates required input fields. |
| `FIELDTYPE` | Sent `input: {candidate: true}`. `In field 'candidate': [Expected type 'T', found true.]` proves the field exists and gives its type; `In field 'candidate': Unknown field.` proves it does not. |
| `AUTH` | Only the `AUTHENTICATION` error came back — the query validated cleanly, so every field and argument in it exists. |
| `EXEC` | The query actually ran unauthenticated and returned data. |
| `404` | Query validated, then failed at execution with `Collection not found` — proves the selection set is valid. |

Anything not listed under "Confirmed" below is **not** confirmed. The "Ruled
out" section lists names proven absent, so nobody re-probes them.

## 3. Confirmed input object types

`!` marks fields the server reports as required. Fields listed without `!` were
confirmed to exist via `FIELDTYPE` and are optional. **Absence from a list does
not prove absence from the type** — only the "ruled out" notes do.

11. **`externalAccountIdentifier`** semantics for the Arena/Pinterest/Tumblr

12. **Actual response payloads** for every mutation. Everything except the
    search queries is auth-gated, so nothing here has been executed end to end.
13. **`AdminMutationGroup`'s 22 fields** are named in the client bundle
    (moderation, triage, bulk delete). Not enumerated here because an MCP for
    moodboarding will not use them.
